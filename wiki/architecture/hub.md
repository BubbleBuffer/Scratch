# Hub server (state)

Build step 4a of the [agent plan](../integrations/agent.md), built 2026-10-08 in [crates/hub](../../crates/hub) (package `notes_hub`, binary `notes-hub`). It runs the same hub as the desktop ([Sync (state)](sync-state.md)) on a server: axum on tokio, plain HTTP inside the container, with Caddy in front terminating TLS. Devices get their token from an OIDC login instead of `--pair`. Since step 4b it also runs the BubblePaw agent ([Agent](../integrations/agent.md)) over its vault replica and serves it at `GET /agent/ws`.

## Running it

For the local amd64 image and the lead's VPS procedure, see [Hub deployment](hub-deploy.md).

- `notes-hub [--config <file>]` serves. The vault replica is `<data_dir>/vault`, created on first start.
- `--devices`, `--unpair <label>`: as `vault-hub`.
- `--pair <label>`: an emergency token that skips the login. It prints a warning to stderr.
- `--agent-token add <name> --scope read|write|everything [--expires 30d|90d|365d|never]` (default 90d), `--agent-token list` (name, tool set, created, expires, last used), `--agent-token revoke <name>` manage agent access. The app manages the same tokens over `/agent-tokens` (below). Each accepts the same `--config <file>` as the server and works while it runs; these commands open the token store without opening the vault.
- Logs go to stdout through `tracing` (`RUST_LOG`, default `info`). One line per request: client address, method, path, status, time. Query strings are never logged, nor are tokens or codes.
- SIGTERM or Ctrl+C stops it gracefully; open `/changes` long-polls end at once.

## Config

A TOML file. Each key can be overridden by `NOTES_HUB_<KEY>` (`NOTES_HUB_OIDC_<KEY>` for `[oidc]`, `NOTES_HUB_AGENT_<KEY>` for `[agent]`). Lists in variables are separated by commas or spaces. Unknown keys are an error.

| Key | Default | Meaning |
|---|---|---|
| `listen` | `0.0.0.0:8080` | Plain-HTTP listen address. |
| `data_dir` | (required) | Holds `vault/` and `agent/` (`agent.data/` for BubblePaw chats, `agent.sqlite` for Notes activity/edit records, `workspace/`). |
| `public_url` | (required with login) | Where browsers reach the hub, e.g. `https://hub.example.com`. The redirect URI is `<public_url>/auth/callback`. Also the base of the page links the tools return (`<public_url>/open/<id>`); unset, they use `http://127.0.0.1:<bound port>`. |
| `android_package`, `android_sha256_certs` | empty | Android App Links. The package (`de.bubblebuffer.notes`) and the SHA-256 fingerprints (`AA:BB:...`, 32 bytes, either case; several for key rotation) of its signing certificates. Set both or neither; with both, `GET /.well-known/assetlinks.json` serves the Digital Asset Links statement for `delegate_permission/common.handle_all_urls`, and with neither that route does not exist. Environment: `NOTES_HUB_ANDROID_PACKAGE`, `NOTES_HUB_ANDROID_SHA256_CERTS` (comma or space separated). The app's manifest verifies `https://hub.example.com/open/*`. |
| `trust_proxy` | `true` | Use the first `X-Forwarded-For` hop as the client address in logs. Set it to `false` if the hub is reachable without Caddy. It affects nothing else: the public URL is configured, not derived from headers. |
| `import_source_limit_bytes` | `67108864` | Per-source tar archive bytes before base64; override with `NOTES_HUB_IMPORT_SOURCE_LIMIT_BYTES`. |
| `oidc.issuer` | empty | Issuer URL (Authentik: `https://<authentik>/application/o/<slug>/`). Empty turns login off, and only `--pair` tokens work. |
| `oidc.client_id` | | The OIDC client ID (required with the issuer). |
| `oidc.client_secret` | empty | Optional: leave it empty for a public client, which signs in with PKCE only (no secret). With a secret the hub is a confidential client and sends it with HTTP Basic auth at the token endpoint. Environment: `NOTES_HUB_OIDC_CLIENT_SECRET` (empty clears it). |
| `oidc.allowed_users` | `[]` | Emails (any case) or `sub`s allowed to sign in. |
| `oidc.allowed_groups` | `[]` | Groups (the ID token's `groups` claim) whose members may sign in. |
| `oidc.scopes` | `openid email profile`, plus `groups` if `allowed_groups` is set | Scopes asked for. |
| `agent.enabled` | `true` | Run the agent. Off: `/agent/ws` answers 503. |
| `agent.default_model` | empty (the agent's default) | `provider/model` for runs that name none and when the vault sets no default model for `hub` (the vault's synced value wins; see [Agent](../integrations/agent.md)). |
| `agent.execution_mode`, `agent.enable_js` | `native`, `false` | Model-facing execution mode (`native` or `js`) and optional JS composition in native mode. Environment: `NOTES_HUB_AGENT_EXECUTION_MODE`, `NOTES_HUB_AGENT_ENABLE_JS`. |
| `agent.bun`, `agent.claude_code_extension` | empty | The `bun` executable and the Claude Code extension folder (holding `src/main.ts`), for the `claude-code` provider. |
| `agent.approvals` | removed | Removed 2026-10-21: hub agent runs use Bypass. A config that still has it (or `NOTES_HUB_AGENT_APPROVALS`) loads, ignores it and prints a deprecation line. |
| `mcp_oauth.issuer`, `mcp_oauth.client_id` | empty | Optional MCP OAuth issuer and client ID. They are the same issuer and client ID as `[oidc]`: one public Authentik provider (no client secret) serves device sign-in and MCP OAuth. Required together, with `public_url`. Environment: `NOTES_HUB_MCP_OAUTH_ISSUER`, `NOTES_HUB_MCP_OAUTH_CLIENT_ID`. |
| `mcp_agent_enabled` | `false` | Enable `/mcp/agent`; requires both MCP OAuth settings. Environment: `NOTES_HUB_MCP_AGENT_ENABLED`. |
| `mcp_agent_default_host` | `hub` | Deprecated and ignored since 2026-10-23: the gateway has no default host. A `?host=` in the URL pins one; without it the connection is any-computer mode. Startup prints a deprecation line when the value is anything but `hub`. Environment `NOTES_HUB_MCP_AGENT_DEFAULT_HOST` is ignored the same way. |

With both allow lists empty every login is refused, and the hub logs a warning at start.

Example (secrets better come from `NOTES_HUB_OIDC_CLIENT_SECRET`):

```toml
data_dir = "/data"
public_url = "https://hub.example.com"

[oidc]
issuer = "https://auth.example.com/application/o/notes/"
client_id = "notes-hub"
allowed_groups = ["notes"]
```

## Routes

| Route | Purpose |
|---|---|
| `GET /health` | `notes-hub` |
| `GET /.well-known/assetlinks.json` | Public. Only with `android_package` and `android_sha256_certs` set (config above): the Digital Asset Links statement, `application/json`. Otherwise no such route. |
| `GET /open/<page id>[?block=<block id>]` | Public (no auth). A 200 HTML page that sends the browser to `notes://page/<page id>[?block=<block id>]`, with an "Open in Scratch" link and a meta refresh fallback. Ids must have the vault's id shape (26 base32 characters, first at most `7`), or the route answers 400. This is the link form agents get from the tools ([links](../../docs/notes/links.md)). The desktop's embedded hub serves the same route from `vault_sync` ([crates/sync/src/open.rs](../../crates/sync/src/open.rs)), and sets the tools' link base to its loopback port when it starts. |
| `/sync`, `/push`, `/changes`, `/blobs/<id>` | The sync protocol, unchanged ([Sync (state)](sync-state.md#protocol)). Paths outside the explicit hub routes fall through to `Hub::handle` on a blocking thread, with the body streamed through a sync reader only after the token check. |
| `GET /auth/start?device=<id>&name=<label>&redirect=<uri>[&state=<s>]` | Starts a login (below). |
| `GET /auth/callback?code&state` | The issuer's redirect back. |
| `POST /auth/redeem` `{code, device}` | Trades a one-time code for `{token, label, account}`. `account` is the signed-in user's email from the verified ID token, or its `sub` when there is none (added 2026-10-11; the deployed hub does not send it yet, so the app shows its fallback). A bad, used, expired or other-device code gets 400 `{"error": "invalid_code"}`. |
| `POST /auth/signout` | With `Authorization: Bearer <token>`: drops that token (204), or 401 if unknown. It also closes that token's agent sockets. |
| `GET /agent/ws` | The agent over a WebSocket (below). |
| `GET /agent-tokens`, `POST /agent-tokens`, `DELETE /agent-tokens/{name}` | List, create and revoke agent tokens from the app. Device token and `X-Device` required, checked like `/sync`; agent tokens and OAuth JWTs get 401. Below. |
| `POST /mcp` | The vault MCP tools over Streamable HTTP (16 listed; 4 are read-only), authenticated by agent tokens, or by Authentik OAuth tokens when the Claude connector is on (below). `GET` and other methods return 405. |
| `GET /.well-known/oauth-protected-resource` and `/.well-known/oauth-protected-resource/mcp` | Protected-resource metadata (RFC 9728) for `/mcp`. Served only when the Claude connector is on. |
| `POST /mcp/agent`, `DELETE /mcp/agent` | Opt-in OAuth-only agent gateway. Vault tools, plus by URL either the pinned host's tools (`?host=<name>`) or, with no parameter, `hosts`, the core computer tools, `tool_search` and `call_tool`. DELETE closes a gateway session. Other methods return 405. Disabled: 404. |
| `GET /host/ws` | Desktops' outbound sockets. Calls for a computer, from either `/mcp/agent?host=<device name>` or `/mcp/agent`, go down its socket (below). Device token and `X-Device`. Gateway disabled: 404. |
| `GET /.well-known/oauth-protected-resource/mcp/agent` | Metadata advertising the separate `/mcp/agent` resource and the existing MCP OAuth issuer; served only when the gateway is enabled. |

## Agent tokens and MCP (`/mcp`)

The repo import is the hidden tool `import_markdown` (write scope, MCP only: never in `tools/list`, not offered to the in-app agent, and sent by the `notes wiki` CLI). It accepts `name`, `roots` `{name, archive_base64, exclude?}` containing plain tar archives, `repo_path`, `git_remote`, `last_activity`, `exclude` and `dry_run`. `create_page` has no import arguments any more; passing `roots` to it returns an error that names `import_markdown`. It finds or creates the Projects database by its `ai.projects` checkbox marker, upserts a row by name and imports under that row (multiple roots have named child containers). Rows hold repo path, git remote, status and last activity; the name is their title. Existing `cut over` status is preserved. Repeated imports reuse page ids and write nothing for unchanged content. Replies contain the row id, row-created/updated flags and an `ImportReport` for each root. `dry_run` diagnoses against a fresh empty temporary vault and labels counts accordingly; it never accesses the real vault's files or export state.

Each registry tool lists the surfaces it is served on (`vault_tools::Surface`: `Mcp`, `InAppAgent`). `feedback_submit` is served on both surfaces; the in-app agent, which the hub's agent host also runs, files its reports with transport `in-app agent`. `feedback_list` (hidden) and `import_markdown` (hidden) are `Mcp` only, and the in-app agent is refused both.

Archive bytes before base64 are capped per source by `import_source_limit_bytes`; an oversized-source error names the source and limit. Only `import_markdown` calls receive the larger archive allowance. Ordinary calls and non-archive JSON keep the 8 MiB limit. Archive paths must be relative; links and special entries are refused.

Agent tokens are separate from device tokens. `<data_dir>/vault/.vault/hub/agent-tokens.json` stores `{name, scope, sha256, created}` entries, plus `expires` and `last_used` (Unix ms) once set. `scope` holds the token's tool set: `read`, `write` or `everything` (files from before tool sets hold only the first two and read unchanged); only creating a token returns the plaintext, once. Names are unique and match `[a-z0-9-]{1,40}`. `list` shows name, scope, creation, expiry and last use, never hashes. A token past `expires` is refused (401 on `/mcp`) and stays listed until revoked. Tokens made before expiry existed never expire. An older hub binary cannot parse a file with these fields (its parser denies unknown fields), so roll back only with the file restored. The same holds for a token with the `everything` set: a hub from before tool sets refuses the whole file (503 on `/mcp`), so revoke such tokens before rolling back. `last_used` is rewritten at most once a minute per token, under the file lock; a failed write is logged and does not refuse the token. Writes use a temporary file and atomic rename, with mode 0600 on Unix. A separate `agent-tokens.lock` serializes mutations across processes, including their reload before saving. Authentication checks the file's modification time and size per request and reloads changes, so revocation takes effect without a server restart. An unreadable or malformed file disables only `/mcp` (503), logs one error per file change without token material, and recovers when repaired; the hub still starts and other routes keep working.

**Managing tokens from the app (`/agent-tokens`).** Any signed-in device may list, create and revoke agent tokens; there is no owner role, since a device token already reads and writes the whole vault. Each call needs `Authorization: Bearer <device-token>` and `X-Device`, checked by the same code as `/sync` (missing device id 400, unknown token 401). Agent tokens and OAuth JWTs are not device tokens and get 401. `GET` returns `{tokens: [{name, scope, created, expires, last_used, expired}], expiry_choices_days: [null, 30, 90, 365], default_expiry_days: 90}`. `POST {name, scope, expires_days}` returns 201 with the token's fields plus `token`, the secret, once; `expires_days` must be one of the choices, `null` never expires and a missing field gets 90. Errors: 400 `invalid_name|invalid_scope|invalid_expiry|invalid_body`, 409 `duplicate_name`, 503 `tokens_unavailable`. `DELETE /agent-tokens/{name}` returns 204, or 404 for an unknown name. Responses are `no-store`, and no token is logged. Source: [agent_token_api.rs](../../crates/hub/src/agent_token_api.rs).

`Authorization: Bearer <agent-token>` is required, unless the Claude connector option below is on. Missing, invalid and expired tokens return plain 401 responses. A token sees and may call only its tool set's tools ([tool_sets.rs](../../crates/tools/src/tool_sets.rs); the same sets as schedules and the in-app agent). The Read set lists the 4 read-only tools (`search_notes`, `read_page`, `memory_read`, `notes_help`) and also permits the read-only hidden and alias names (`feedback_list`, `list_pages`, `backlinks`, `agenda`, `overdue`, `query_database`, `memory_search`, `memory_list`); other calls return JSON-RPC error -32602 `tool not available in read-only scope: <name>`, and the tool does not run. The Write set lists all 16 tools and permits every vault tool name, including `import_markdown`. The Everything set permits every tool the surface serves, including tools added later; on `/mcp` that is the same as Write today. Every request carrying `Origin` is refused with 403, including localhost origins, unless the Claude connector option is on; this route sends no CORS headers.

**Claude connector option (off by default; `[mcp_oauth]`).** A bearer token that is not an agent token (on a request without `X-Device`) is checked as an access token from the same Authentik provider that serves device sign-in: an offline JWT check against the `[mcp_oauth]` issuer (the `[oidc]` issuer), then the same allow-list as app login. Connectors need only the provider's client ID, since the provider is public and has no client secret. Allowed accounts get the Everything tool set, and their edits are recorded as `oauth:<email>` (or `oauth:<sub>`). Without a valid token, `/mcp` answers 401 with `WWW-Authenticate` pointing at the protected-resource metadata; a token outside the allow-list gets 403. Setup and limits: [Claude connector](../integrations/ai-assistants.md#claude-connector).

The hub and desktop use the same transport-independent JSON-RPC handler in [vault_mcp](../../crates/mcp/src/server.rs): initialize, tool lists and calls, errors and notifications. Replies are plain `application/json`; notifications return an empty 202. There are no sessions or SSE streams; ordinary bodies are limited to 8 MiB, with the per-source archive allowance described above for repo imports. Calls use the hub's existing shared vault on a blocking task. Writes record `agent:<name>` in the existing page peer map and history's `Version.device`, with a scoped identity per synchronous call and no sync or history format change. Device writes retain their device identity. The Flutter history panel still displays nonlocal identities as "Another device". The endpoint is available independently of the BubblePaw `[agent].enabled` setting.

**Device calls on `/mcp`.** A request with an `X-Device: <device id>` header is checked as a signed-in device's token, exactly as `/sync` checks it, and never as an agent or OAuth token. Such a request may call only the `jobs` tool; any other tool returns the error "a device token calls only the jobs tool on /mcp". Its actor is `device:<id>` and its tool set is Everything, but each job it creates runs with the hub runner's set (see [Jobs](#jobs)). A device token that fails the check gets 401.

## Agent MCP gateway (`/mcp/agent`)

**Implemented; no deployment or real connector sign-in is established here.** `https://hub.example.com/mcp/agent` is a separate, opt-in endpoint backed by the vault registry and the embedded agent's BubblePaw runtime. `/mcp` retains its vault tools, static agent tokens and stateless transport. Source: [mcp_agent.rs](../../crates/hub/src/mcp_agent.rs), [gateway.rs](../../crates/agent/src/gateway.rs).

- **Enable and modes.** Set `NOTES_HUB_MCP_AGENT_ENABLED=true`; this requires the existing MCP OAuth issuer/client configuration. Vault tools match `/mcp` and never take `host`. The URL picks the mode: `?host=<name>` pins one host (`hub` or a computer's name) and lists that host's tools; no parameter is any-computer mode (`hosts`, the core computer tools with a required `host`, `tool_search`, `call_tool`). There is no default host. An unknown or offline name is a call error, never a fallback. An unavailable embedded agent produces an error rather than falling back to another host. The hub registers no desktop tool pack and has no shell tools.
- **Authentication.** OAuth bearer tokens only; static agent and device tokens are not accepted. It reuses `/mcp`'s issuer, audience validation and app-login allow-list (`oidc.allowed_users` or `oidc.allowed_groups`, in practice `notes-users`). The JWT `aud` must contain the configured client ID. Additional resource audiences `<public_url>/mcp`, `<public_url>/mcp/agent` and `<public_url>/mcp/agent?<query>` are accepted on both endpoints; a resource audience alone is refused. The issuer is the `[oidc]` issuer (`https://auth.example.com/application/o/<slug>/`). The provider is public, so connectors send its client ID and no client secret, with PKCE S256. A 401 challenge points to `/.well-known/oauth-protected-resource/mcp/agent`, whose resource is `<public_url>/mcp/agent`. URL host selection is preserved in discovery: `?host=hub` appears on both the challenge metadata URL and its advertised resource URL, and that query-bearing resource audience is accepted across both endpoints while the configured client ID remains required in `aud`. Accounts outside the allow-list get 403. Requests without an Origin header pass; a single Origin of `https://claude.ai`, `https://claude.com` or `https://chatgpt.com` passes; others or multiple Origins get 403. Existing OAuth callbacks still govern connector login. See [connector setup](../integrations/ai-assistants.md#agent-gateway-connector).
- **Tools.** Vault tools use the exact `/mcp` registry, schemas and HTTP dispatcher, including imports, aliases, limits and actor attribution. The agent's own vault adapters remain unchanged but are omitted from the additional host list using registry-derived names. Other name collisions fail discovery. Host definitions come from BubblePaw's `Harness::effective_tool_definitions`, with gateway exclusions and current permission policy applied; calls use `Harness::call_tool` without a model turn. The hub defaults to native mode without JS. `[agent] enable_js = true` additionally offers `js` and `js_help`; `execution_mode = "js"` selects legacy mode. The local in-app agent retains JS. In any-computer mode `hosts` returns `[{name, online}]` for every computer seen since start. A pinned `?host=hub` lists the hub runtime's own `hosts`, which returns only `hub`. When JS is offered, `js_help` discovers its capabilities and runtime guidance, and `tools.hosts()` remains available inside JS. Tools requiring interactive approval are absent and refused, including nested JS calls. `history_*`, web tools, `ui_*`, `todo`, `question` and `reload` are excluded.
- **Sessions.** Initialize returns a new `Mcp-Session-Id` bound to the OAuth subject. Each HTTP session owns a distinct agent session and persistent JavaScript environments; client-supplied chat IDs cannot select them. Host tool execution requires that header; vault calls, discovery and help do not. A concurrent call in the same session receives a busy error. DELETE can cancel an active host call or JS cell. DELETE with the header closes the session and environments. Sessions expire after 24 hours idle; a later initialize reclaims expired sessions. There are at most 256 HTTP sessions. Restart loses the HTTP session mapping, so clients must initialize again. Persistent JavaScript state does not imply restart recovery.
- **Transport.** POST and DELETE only, JSON replies, empty 202 notifications and no SSE stream; ordinary request bodies are limited to 8 MiB; vault imports use the same per-source archive allowance as `/mcp`. Vault calls and `hosts` remain usable when the embedded agent is unavailable; initialization and host execution require it.

To switch an existing OAuth connector, change `https://hub.example.com/mcp` to `https://hub.example.com/mcp/agent?host=hub` (the hub runtime), another `/mcp/agent` address (`?host=<computer>` or none), or back, retaining the same client ID and login. Both routes share issuer, accepted audiences, allow-list, scopes and registered redirect URIs. The same valid OAuth token is accepted across both routes; the server does not bind it to a metadata resource URL. Static agent tokens remain specific to `/mcp`. See [switching instructions](../integrations/ai-assistants.md#switch-an-existing-connector).

Computers are reached through the host relay below. A name the hub does not know is an error, not a route to a computer.

## Host relay (`/host/ws`)

Built 2026-10-22. Source: [hosts.rs](../../crates/hub/src/hosts.rs), wire types in [agent_wire/src/host.rs](../../crates/agent_wire/src/host.rs). The desktop side is in [agent.md](../integrations/agent.md#pc-host-relay-hostcomputer-built-2026-10-22).

- **Auth and name.** `Authorization: Bearer <device token>` and `X-Device`, checked like `/agent/ws` before the upgrade (missing token: 401). The host's name is the device's label on the hub; an empty label or `hub` gets 409. The token is re-checked on every ping; signing the device out closes the socket.
- **One per name.** A new connection under the same name replaces (closes) the old one. A closed socket leaves the name listed with `online: false`; calls fail with "<name> is offline". Nothing is kept across hub restarts.
- **Protocol.** JSON-RPC 2.0, one text frame per message, roles reversed from `/agent/ws`: the hub sends requests, the desktop answers. `tools {session?}` gives `{tools: [{name, description, input_schema, read_only}]}`; `call {session, name, arguments, caller: {id, name?}}` gives `{content, is_error, pending}`; `close_session {session}` ends the desktop's session for that MCP session (sent on DELETE and when the gateway session expires). `cancel {id}` is a notification naming a request to stop.
- **Routing.** `/mcp/agent` sessions that select a connected host list its tools with `tools` and send each host tool call as `call`, with a session id of their own. `js_help` is not offered for a desktop host. Calls time out after 10 minutes (`cancel` is sent and the call fails); `tools` and `close_session` after 30 s.
- **Processes.** In any-computer mode the hub remembers which computer started each `exec` process, by handle, for the last 4096 handles, in memory. `poll`, `wait` or `cancel` on another computer is refused and names the computer that started it. A desktop keeps its processes per relay session, so one MCP session's process cannot be polled from another.
- **Liveness.** Pings every 30 s; 90 s of silence drops the socket.
- **Tools offered.** Whatever the desktop's relay engine registers: its desktop pack and its MCP servers' tools ([agent.md](../integrations/agent.md#mcp-servers-on-the-desktop-built-2026-10-22)), all run without prompts. The hub needs no change for MCP: the desktop lists them in its `tools` answer, and the list follows the desktop's MCP settings live (no reconnect).

## Agent (`/agent/ws`)

The hub opens one `vault_agent::Agent` on its shared `Arc<Vault>`, at start when enabled, and serves it to every device. The DTOs, method names and envelopes are in [crates/agent_wire](../../crates/agent_wire) (`notes_agent_wire`), shared with the app's bridge. Transport-free method dispatch, event subscriptions and the 1024-event gap buffer are in [`vault_agent::rpc::Dispatcher`](../../crates/agent/src/rpc.rs); this module has no axum or authentication dependency. The hub retains lazy opening, authentication, socket frames, pings and sign-out closing. Both hosts use `Agent::open`; the hub sets `host_kind = Hub` and `packs = []`, without a desktop pack setting.

- **Opening.** If the agent fails to open, the failure is logged, sync keeps working, `/agent/ws` answers 503 with the reason, and the next connection tries again.
- **Auth.** `Authorization: Bearer <token>` and `X-Device: <id>`, checked by `Hub::handle` exactly as sync checks them, before the upgrade. No token gets 401; a bad token or wrong device gets sync's status (401 or 403). Tokens are never read from the query string and never logged. The tokens are checked again at every ping, so a socket whose token was replaced closes within 30 s. Sign-out closes that token's sockets at once. `--pair` and `--unpair` from another process take effect at the next token check, as for sync; token file saves reload under a stable `tokens.lock` and use atomic rename with mode 0600 on Unix.
- **Frames.** JSON-RPC 2.0, one text frame per message. Requests `{"jsonrpc":"2.0","id":n,"method":…,"params":…}` are answered in any order, each on its own blocking task.
- **Methods.** `host_info`, `models`, `sessions`, `create_session {title}`, `rename_session {session_id,title}`, `delete_session`, `session_state`, `send {session_id,text,model?}`, `steer {session_id,text}`, `cancel`, `decide_approval {approval_id,decision,reason?}`, `events_after {after,session_id?}`, `run_script {session_id,label,code}`, `subscribe`, `unsubscribe` (the bare session methods take `{session_id}`). Also: `projects_list`, `project_add {name,path}`, `project_remove {id}`, `project_rename {id,name}`, `session_project_set {session_id,project_id}`, and `permission_mode_set {mode}`. Results are the bridge's DTOs in snake_case. Project add/rename return a project `{id,name,path,added_at}`, remove returns null, and session project set returns the updated session (including optional `project_id`/`project_name`). These project methods return "not supported on this host" on the hub, which has no desktop pack. User-initiated project management does not request tool approval. `permission_mode_set` returns and persists the new mode (`manual`, `auto` or `bypass`); it applies from the next message/run without reopening the agent, while an active run retains its original policy.
- **Host capabilities.** `host_info` returns `{kind, packs, tools, providers, can_run_tasks, version, permission_mode, projects, default_model}` (`default_model`, added 2026-10-22, is the host's configured default, the hub's `[agent] default_model`; older hosts omit it): on this hub `kind` is `hub`, `packs` is empty, `exec` is absent, and both `can_run_tasks` and `projects` are false. Desktop hosts add the optional desktop pack and report `projects: true`. Clients query this method to decide task and project availability. These new methods and capability fields require redeploying the hub; the desktop relay (4d) is not implemented. Permission mode is agent-wide; with no Confirm tools it has no effect on ordinary hub tools.
- **Origin.** The server sets the run's client to the device id, named by the token's label. Events carry it as `origin_id` / `origin_name`.
- **Events.** After `subscribe`, the socket gets `{"jsonrpc":"2.0","method":"event","params":<AgentEvent>}` for every event, live `paragraph` deltas included. Each socket buffers 1024; when full, events are dropped and one `gap` event (`skipped`, `sequence` = the last durable seq delivered) follows when there is room, so the client catches up with `events_after`.
- **Errors.** `{code, message, data:{kind, resets_at?}}`, with the bridge's error strings as `message`. Codes: -32700 parse, -32600 invalid request, -32601 unknown method, -32602 bad params, -32000 agent error. `kind` is `session_busy`, `not_found`, `provider_auth` or `rate_limit` (with `resets_at`); `not_found` is detected from the agent's error text.
- **Liveness.** The server pings every 30 s and drops a socket after 90 s without a frame. A device may hold several sockets. Shutdown closes every socket, then the agent.

### Agent tooling API (Part A, 2026-10-09)

The hub and desktop share the additional tooling contracts in `notes_agent_wire`:

- `session_state` includes `activity` and `edits`. Activity entries carry run/call IDs, order, tool name, summary, error state and an optional edit ID. Edit records expose page identity, kind, added/removed counts, line-diff hunks, changed block IDs and undo state; full before content is not sent to clients.
- `edit_undo {edit_id}` restores an agent change as a new vault change and returns the updated edit record. It refuses an intervening page change with `page changed since the agent's edit; use page history`.
- `send {session_id,text,model?,context?}` accepts `context: {pages:[{id,title}],selection?:{page_id,page_title,block_ids,text}}`. User transcript entries expose `text` and parsed `context` separately; selection text is capped at 4,000 characters before the model sees it.
- `subscribe {session_id?}` retains the normal event stream and optionally marks the client as viewing one session. Only clients explicitly viewing the session count as a UI recipient; unsubscribe, replacing the stream or disconnecting clears that presence.
- Page tools notify viewers with `{"jsonrpc":"2.0","method":"ui_action","params":{"session_id":"…","run_id":"…","action":"open_page","page_id":"…","block_ids":[]}}`. The other action is `highlight`. These notifications are transient; tool activity and edit records persist in the agent database.
- `host_info.tools` lists the task, daily-note and page UI tools on both hosts. The hub still has no desktop filesystem or process tools and starts in Bypass.

Deploying these methods, snapshot fields and notifications requires a hub redeploy. Part B will add the Flutter UI that consumes them; no deployment is performed in Part A.

## Jobs

Outside agents, and the app's Ask AI and Agent-assigned tasks (through a signed-in device's token), start runs of the hub's agent and collect their results later, through one listed tool, `jobs`. Its actions are `create` (`prompt`, optional `tools`, `page` and `after`), `get`, `wait` (`timeout_ms`), `cancel` and `list` (`limit`). It is served on `/mcp` (agent tokens, OAuth and device tokens with `X-Device`) and `/mcp/agent` (OAuth), and the `notes jobs` CLI calls it on `/mcp`. It has no HTTP routes of its own and is not served to the in-app agent. A desktop's local MCP server answers it with "jobs run on the hub: connect to the hub's /mcp with an agent token". For the calling agent, see [docs/notes/jobs.md](../../docs/notes/jobs.md) (`notes_help` topic `jobs`).

- **Enabled.** `create` needs `[agent] enabled` (on by default) and is refused otherwise. The Read set can't call `jobs` at all (the tool is not read-only), so a Read token can't create a job.
- **Pages.** `create` may name a page (`page`, a page id) and a block on it (`after`, a block id). `after` without `page` is an error; an unknown page gives "no such page". A job with a page puts a placeholder in the page, and its result (completed, failed, cancelled or interrupted text) replaces the placeholder. The job reports `page`.
- **Tool set.** A run gets the caller's tool set, narrowed by the hub runner's set (Settings > AI > Agent > Tools, with Run AI on: Hub). A device's jobs have no set of their own and get the hub runner's set (`tool_sets.hub`, default Everything). `create` with `tools` narrows it further; asking for more than the caller's own set is refused. The run never asks for approval and has no tools outside its set.
- **Engine.** The hub keeps one job engine per tool set: an `Agent` opened with `AgentConfig.tool_set`, which registers exactly that set's vault tools, in Bypass, with its sessions under `<data_dir>/jobs/<set>/`. There is no plan or approval step. Each run is `Agent::run_job`, with the time limit below.
- **Storage.** A job is a row of the "AI tasks" database. The storage is [crates/mcp/src/jobs.rs](../../crates/mcp/src/jobs.rs), over the database code in [crates/mcp/src/tasks.rs](../../crates/mcp/src/tasks.rs). The row's text properties are `node` (`hub`), `owner`, `tools`, `session` and `finished`; the row body holds the result. An older database gains these properties and the `cancelled` and `interrupted` statuses on first use (`tasks::migrate_schema`). Desktops never claim a row with a node, so only the hub runs jobs.
- **States.** `queued`, `running`, then `completed` (stored as `done`), `failed`, `cancelled` or `interrupted`. A completed job carries `result`; a failed or interrupted job carries `error`. `cancel` ends a queued or running job as `cancelled`.
- **Ownership.** The owner is the principal that created the job: `agent:<token name>`, `oauth:<email, or sub>` or `device:<device id>`. Only the owner sees, waits for or cancels a job; any other agent caller gets "no such job". Any signed-in device may list and cancel device-created jobs; agent tokens never see them. Devices see every job and its result as rows through sync.
- **Limits.** One running job per creator; later jobs wait queued, oldest first. At most 4 queued jobs per hub, and `create` is refused while the queue is full. `wait` blocks at most 60 s (default 30 s). A run stops after 1 hour and its job fails with a limit message. Ended jobs are kept 30 days, then trashed.
- **Restart.** A hub restart marks running jobs `interrupted`. They are not started again.
- **Not built.** Steering a running job and sending it follow-up messages are a later phase.

## Login sequence

1. The app opens `/auth/start` in a browser. `redirect` must be exactly `http://127.0.0.1:<port>/done` (port 1024–65535; the desktop's loopback listener) or `notes://auth` (Android). Queries, fragments, other paths, `localhost`, and alternate spellings that URL parsing could normalize are refused. Anything else, or a device id that is not 1–128 letters, digits, `-`, `_` or `.`, gets a 400 page. `name` is cut to 64 characters.
2. The hub makes a state, a nonce and a PKCE verifier (S256), keeps them in memory for 10 minutes, and redirects to the issuer's authorize endpoint, found through discovery (cached for 10 minutes).
3. `/auth/callback` takes the started login (single use). An unknown or expired state shows a small HTML error page. Otherwise every failure redirects to the app with `error=` and the app's `state`:
   - `<the issuer's error>` when the issuer sent one
   - `login_failed`: the code exchange (HTTP Basic with the client secret when one is configured, otherwise `client_id` in the body; plus the verifier) or the ID token check failed. The `openidconnect` crate checks the signature through the JWKS, `iss`, `aud`, `exp` and `nonce`.
   - `access_denied`: the user is in neither allow list
   - `device_refused`: the device id is the hub's own
4. On success the hub creates a device token with `Hub::login_device` (label `<name>`, bound to the device; re-login replaces the device's old token; a clashing label gets ` (2)`) in the usual `tokens.json`, and redirects to `redirect?code=<one-time code>&state=<app state>`. The code is 256 random bits, single use, valid for 2 minutes.
5. The app posts the code with its device id to `/auth/redeem` and stores the token. It then syncs as any paired device, over `https://`.

## Security notes

- Started logins and codes are kept in memory under the SHA-256 of their secret, so a restart cancels logins in progress. At most 10,000 started logins are kept.
- Token hashes and the redeem device are compared in constant time.
- Auth responses carry `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. No cookies are used.
- The OIDC HTTP client follows no redirects (as `openidconnect` requires) and times out after 15 s.
- The token for a login is written at the callback. If its code is never redeemed, the entry stays until the device logs in again or is unpaired.
- An email in `allowed_users` matches whether or not the issuer marks it verified (Authentik sends `email_verified: false` by default). Prefer `allowed_groups` or a `sub`: an email match is only safe while nobody else can set that email in Authentik (no self-enrollment or editable emails).
