# Agent (BubblePaw)

## Chat search source

**Built 2026-10-12 ([note types, refactor 6](../architecture/note-types.md#preparatory-refactors)):** chats participate in the vault's search as the external `agent` source, type `chat`, while their transcript and outline storage remain outside the vault. Each chat contributes a title row; each outline chapter and section contributes its display name and summary. Names use the shared name/gist helper, and raw message text is never indexed. Hub chats contribute title rows only because their outlines are not available yet.

Rows are identified by the session and message-anchor IDs, never titles. A rename rewrites the labels in place; deletion removes the chat's rows. Outline revision changes refresh the source, including chats that are not visible. Search title presentation follows the backend the active agent opened on: switching the test's platform to phone layout cannot change local name/gist labels into raw Hub titles. Explicit user names still remain intact. A complete startup reconciliation clears stale rows from an earlier process; failures to read the agent preserve cached search rows. Vault reindex and clear preserve these external rows.

`AgentStore` initializes the vault sink automatically. Visible outline loads and session-list refreshes trigger a sweep; a five-second sweep checks closed chats too, using the existing per-session revision. Sweeps coalesce and serialize their writes; deletion tombstones prevent an in-flight read from restoring a removed chat. Shutdown drains writes before the vault closes. Writes are currently per row, so startup reconciliation briefly clears the source before rebuilding it.

Ctrl+K and mobile search group Pages and Chats. Chapter hits show `Chat title › Chapter name`; section hits add `› Section name`, with no numbers. The result target carries the session ID and first/last message IDs, and activation uses the existing jump-to-anchor path. `type:chat` and the Chats chip limit results to chats; document and database filters are also available. The [Agent add-on](../addons/agent.md) now registers this source, the chat type and its presentation builders; broader view integration remains proposed. See [search operators and source API](../architecture/search-queries.md).

## Agent MCP gateway (`/mcp/agent`)

**Implemented; deployment and real connector sign-in are not established here.** The separate endpoint `https://notes.example.com/mcp/agent` exposes the vault tools and the embedded agent's model-facing host tools to an external assistant. The existing `/mcp` endpoint keeps its vault tools and agent-token behavior. Host tool calls run through BubblePaw's single-tool API (`Harness::call_tool`) without invoking a model or provider; see [gateway runtime](../../crates/agent/src/gateway.rs) and [HTTP adapter](../../crates/hub/src/mcp_agent.rs).

The MCP tool list is the `/mcp` vault tools (same registry, schemas and dispatcher; they never take `host`), the selected host's tools as BubblePaw's `effective_tool_definitions` advertises them, and `hosts`. The agent's own vault adapters are left out of the host list by their registry names; any other name collision fails discovery. The hub host runs `execution_mode = "native"` without JS by default; `js` and `js_help` appear only when the host enables JS. Every host tool accepts an optional `host`. Selection follows this order: tool argument `host`, request URL `?host=name`, the vault's synced default runner (`hub` or `this_device`, both meaning `hub` here), `NOTES_HUB_MCP_AGENT_DEFAULT_HOST`, then `hub`. Unknown URL/configured hosts produce a call error listing available hosts, without silent fallback. The hub itself has no desktop tool pack or shell access; a desktop with "Let the hub use this computer" on is a host too (below).

`hosts` returns `[{name, online, default}]`, marking the selected host. When JS is offered, use `js_help` without a query to list callable signatures and descriptions, beginning with the host list, with a tool name or search phrase for schemas and documentation, or with `query: "js"` for the runtime reference. Inside `js`, `tools.hosts()` returns `[{name, online, default}]` for the current call, with the effective host marked as default. Call host tools as `tools.*`, including `tools.environments` to manage environments. Offered capabilities come from the selected host's actual registry and current permission policy. Tools that would ask for confirmation are omitted: this gateway has no approval UI. It also excludes `history_*`, web tools and `ui_*`, including `ui_open_page` and `ui_highlight`. Notes does not register `todo`, `question` or `reload`; the gateway does not add them.

Initialize over HTTP to receive `Mcp-Session-Id`, then send that header with host tool calls; vault calls, discovery and `hosts` do not need it. Each session is bound to the authenticated OAuth subject and has its own persistent JavaScript environments; it cannot select an existing chat's session ID. `DELETE /mcp/agent` with the header closes the session and its environments. Sessions expire after 24 hours idle, with expired sessions reclaimed on a later initialize. A hub restart requires initializing again; persistent state is not a promise of restart recovery.

The gateway is disabled by default. Enable `NOTES_HUB_MCP_AGENT_ENABLED=true` with the existing MCP OAuth issuer/client configuration; [connector setup](ai-assistants.md#agent-gateway-connector) lists the URL, client ID and metadata path. Static agent tokens and device tokens do not authenticate this endpoint.

To switch an existing OAuth connector, edit its URL from `https://notes.example.com/mcp` to `https://notes.example.com/mcp/agent?host=hub`, or back. Keep the same client ID and login: both routes share issuer, accepted audiences, allow-list, scopes and registered redirect URIs. The JWT `aud` must contain the configured client ID; optional resource audiences `/mcp`, `/mcp/agent` and `/mcp/agent?<query>` under the public hub URL are accepted across both routes. A resource audience alone is refused. The same valid OAuth token is accepted by either route; the server does not bind it to the selected endpoint. See [switching instructions](ai-assistants.md#switch-an-existing-connector).

Desktop outbound relay remains unimplemented. Later desktop integration needs an authenticated outbound connection from the desktop to the hub, host registration and availability reporting, and routing that preserves each host's registry, permission policy and session ownership. Setting `host: "desktop"` alone does not provide desktop access.

## PC host relay (`?host=<computer>`, built 2026-10-22)

From ChatGPT or claude.ai connected to `https://notes.example.com/mcp/agent?host=<computer>`, the host tools run on that computer: its desktop pack (`read`, `write`, `edit`, `exec`, ...) and whatever else its agent registers, next to the hub's vault tools.

- **Toggle.** Settings > Sync, under the hub sign-in, desktop only: "Let the hub use this computer". Off by default, stored in this device's `settings.json` (`hubUsesThisComputer`), never synced. It needs a sign-in to an `https://` hub. On connects; off, signing out or closing the app disconnects. Off means nothing of this computer is exposed.
- **Host name and address.** While the toggle is on, Settings shows below it "Appears on the hub as <name>": the hub's label for this device (`clientDeviceLabel`, this computer's name at sign-in; there is no rename). The hub matches `?host=` against it exactly. Below that is the relay's connection state (connected, connecting, or the last error while it retries; read from the relay engine's `host_relay_status` every 2 s while Settings shows it) and the full connector address `<hub>/mcp/agent?host=<name, URI-encoded>` with Copy, e.g. `https://hub.example.com/mcp/agent?host=Work%20PC`. Source: [host_relay_status.dart](../../app/lib/addons/agent/host_relay_status.dart).
- **Connection.** The desktop keeps one outbound WebSocket to the hub's `GET /host/ws`, authenticated with its device token and `X-Device` like `/agent/ws`, and reconnects with backoff (1 s doubling to 30 s). It registers under its device name on the hub (the token's label), which is the `host=` value; `hosts` lists it with `online`. Protocol: [hub.md](../architecture/hub.md#host-relay-hostws).
- **Engine.** The relay opens its own agent engine with its own store (`<data dir>/host-relay/`), so it never contends with the chat engine and relay sessions stay out of the chat list. Its tools follow the AI settings like the chat engine (desktop tools and their root), run natively (no JS) under Bypass with no prompts, and use the same gateway exclusions as the hub host. Each MCP session gets one relay session on the computer, closed when the MCP session ends or the socket drops. Source: [host_relay.rs](../../app/rust/src/host_relay.rs), [host_relay_link.dart](../../app/lib/addons/agent/host_relay_link.dart).
- **Who may call.** Only OAuth logins on `/mcp/agent`. Agent tokens and device tokens cannot reach a host (`/mcp` has no host routing, and `/host/ws` only accepts hosts).
- **Limits.** One connection per computer: a reconnect replaces the old one. Each call times out after 10 minutes and is then cancelled on the computer. A call to a computer that is not connected fails with "<name> is offline". The hub keeps no host state across restarts. Phones are never hosts; steer, follow-up and read-only logins are out of scope.

## MCP servers on the desktop (built 2026-10-22)

The desktop agent can use MCP servers through BubblePaw's MCP client (`bubblepaw-mcp`). Source: [mcp.rs](../../crates/agent/src/mcp.rs).

- **Settings.** Settings > AI > Agent, next to the tool sets, desktop only: "MCP servers". Each server has a name, a type and an on/off switch. A Command server has a command, arguments (one per line) and environment variables (`KEY=value` lines); a URL server has a URL and headers as `Header=ENV_VAR` lines, whose values BubblePaw reads from that environment variable on this computer (the name must end in `_API_KEY`, `_KEY` or `_TOKEN`; there are no literal header values). Add, Edit and Remove check that the name is non-empty and not taken and that a command or URL is set; the engine checks the rest and its refusal shows in the section. Each row shows the chat engine's state for that server: running with its tool count, failed with the error, or off. The section says so when the agent is not open on this computer or the tool set is not Everything. Source: [agent_mcp_settings.dart](../../app/lib/addons/agent/agent_mcp_settings.dart).
- **Storage.** This device's AI settings (`ai_settings.json`, `agentMcpServers`), never the vault: an object of server name to BubblePaw's `McpServerSettings` as JSON (`command`, `args`, `env` or `url`, `headers_from`, `enabled`, and `cwd`, `env_from`, `approval`, timeouts and tool include and exclude lists, which the UI keeps unchanged when it edits a server).
- **Applying changes.** The app gives the list to the chat engine and the relay engine (`set_mcp_servers`) right after each opens and on every change. Each engine restarts only the servers that changed; chats, the gateway and the relay's tool list follow at once, with no app restart and no relay reconnect.
- **mcp.toml.** An `mcp.toml` in the data directory (BubblePaw's `[mcp.servers.<name>]` format) is imported once when the desktop app starts: its servers are added to the settings unless the name is taken, and the file is renamed to `mcp.toml.imported`. The app does not read it again. A file that can't be read or parsed is logged and left in place.
- **Startup.** Servers start when the engine opens (or when the list changes), in parallel. A server that fails to start (bad command, handshake error, timeout) is logged, shown as failed with its error in Settings, and left out; the agent opens without it and the other servers run. Stdio servers run with the agent workspace as their working directory unless `cwd` says otherwise. Before each turn the engine re-reads the servers' tool lists, so `tools/list_changed` takes effect on the next turn. Closing the engine stops the servers.
- **Who gets them.** Desktop engines with the Everything tool set only; the hub never starts MCP servers. In-app chats see the servers' tools like the desktop pack. The hub relay engine opens the same servers (its own processes) and offers their tools to `/mcp/agent?host=<computer>`; the relay's tool list follows settings changes live.
- **Approval.** The in-app agent and the relay both run under Bypass, so a server's `approval = "confirm"` (BubblePaw's default for MCP tools) does not prompt: the tools run at once, in chats and from ChatGPT or claude.ai through the hub. This is the approved Everything and Bypass behaviour; a server that should not be reachable that way stays off or out of the list.

## Hub jobs

Jobs started through the hub's `jobs` tool ([Jobs](../architecture/hub.md#jobs)) reuse this runtime with a fixed tool set. The hub keeps one engine per tool set: an `Agent` opened with `AgentConfig.tool_set` set, so it registers only that set's vault tools. Its sessions live under `<data_dir>/jobs/<set>/`, apart from chats. The engine runs in Bypass, so a job never prompts for approval. `Agent::run_job` runs one prompt in a session and waits for it. A run still going at the time limit (1 hour on the hub) is cancelled and reported as timed out, which the job records as failed. The outcome is completed with its text, failed, or cancelled; the hub's job worker writes it to the job's row. The app's Ask AI and Agent-assigned tasks start the same kind of job from a signed-in device; see [AI tasks](ai-assistants.md#ai-tasks).

## Agent tools and activity

**Current state (Part A, 2026-10-09):** the Rust tools, wire protocol and Local/Remote bridge provide the data for the later Flutter UI. This part adds no visible app controls. For now the agent always runs in Bypass; permission modes exist in vault_agent but are not exposed until BubblePaw's permission model is refined.

- **Agenda:** `agenda {from,to}` accepts ISO calendar dates, with `from` inclusive and `to` exclusive, and a span of 1 to 62 days; `overdue {}` returns the same item shape and compares timed items with now and all-day items with today's calendar boundary. Each item includes a stable `block:<page>/<block>` or `row:<database>/<row>` reference, title, date, optional time, done state, kind and page identity. `set_done {item,done}` and `reschedule {item,date,time?}` use those references. Rescheduling changes the first date mention on a to-do, appending one if absent, or changes a row's agenda date property. Dates and optional `HH:MM` times use the host's local calendar; a time lets the app's existing reminder planner notify the user. `daily_note {date?}` creates a note with empty Tasks and Log toggle sections once, bypassing the Journal's default template, and then reuses that day's note. There is no separate reminder entity or reminder tool.
- **Edit records:** every mutating vault tool records the affected page before and after in the agent's SQLite database, `<data_dir>/agent/agent.sqlite`. The snapshot exposes compact line-diff hunks with up to three context lines, added/removed counts, changed block IDs and an undo state; full undo content stays on the host. Changes to the same page in one run merge from the first before state to the latest after state. `edit_undo {edit_id}` is a user API, not an agent tool: it restores content as a new change, trashes an agent-created page or restores a trashed page. An intervening change refuses undo with `page changed since the agent's edit; use page history`. These records supplement the vault's device-grouped history; the agent still uses the existing device peer.
- **Activity:** session snapshots expose tool calls, human summaries, error state and linked edit IDs, including calls nested inside `js` while omitting the `js` wrapper. The adapter persists activity at invocation boundaries for all registered host tools (including history and environment), except `js`. BubblePaw's nested progress is live-only and is not persisted. Write calls keep BubblePaw's original call IDs; read calls get stable adapter invocation IDs. Existing progress events tell clients to refresh the snapshot.
- **Tool summaries:** `search_notes` reports “Searched notes”, native `search` reports “Searched files”, `read` reports “Read”, `write`/`edit` report “Edited”, and `list` reports “Listed”, with the query or path. The Flutter work line groups both searches as Searched and distinguishes page reads from file reads, file edits and directory listings. Edit records remain vault-only.
- **Showing pages:** `ui_open_page {page,block?}` and `ui_highlight {page,blocks}` validate the page and block IDs and send a `ui_action` notification to clients explicitly subscribed to that session. Without a viewing client the tools report `no app is showing this chat; nothing opened`. A global event subscription alone does not mean a chat is being viewed. The agent uses these tools when helpful, rather than opening every page it reads.
- **Message context:** `send` accepts attached page identities and an optional quoted selection. The model receives compact JSON in `<notes-context>` before the message; selection text is capped at 4,000 characters. Transcript conversion in Rust separates the user's text from the parsed context so Part B can render attachment chips without parsing prompt text in Dart.
- **Desktop file tools (BubblePaw native tools, since 2026-10-20):** `edit` replaces an exact string (`path`, `old_string`, `new_string`, optional `replace_all`) and `write` writes a whole file (`path`, `content`). There is no `expectedSha256` precondition. Paths must be relative to the session's project root; absolute paths are refused, even inside the root.
- **Runtime notices:** BubblePaw stores per-step runtime notices (`[host notice] ...`) as generated user messages. They are model context only: session snapshots, the app's chat data, chat context sent to other chats, and replay all skip them.
- **Store layout:** BubblePaw keeps chats in `<data_dir>/agent/agent.data/` (catalog, serving database and one database per chat) and migrates an older single-file `agent.sqlite` on first open. Notes' own edit and activity records stay in `agent.sqlite`. Event sequences jump to a new block after a restart, so a cursor from before the restart gets `resync`.
- **Not here:** web search, fetch and research tools belong to BubblePaw; none are added here. Flutter edit rows, activity, context and page actions are described below.
- **Limits:** the daily-note "created" classification uses an existing-note precheck that can race external UI creation. Undo checks content and metadata, then restores through existing core APIs, not an atomic conditional restore. Failed creations before a page ID is returned can lack an edit record. No BubblePaw change was made.

Sending on Android first waits for pending page saves, flushes the vault and completes a sync round. A sync failure is shown instead of asking the agent to use a stale replica. Run completion asks sync to pull promptly; imported edits reach the editor through the existing change feed. Signing out clears the account/token and cached Hub chat IDs, without falling back to a local engine.

The in-process test in [local_workflow.rs](../../crates/hub/tests/local_workflow.rs) uses a mock OIDC issuer and scripted model: device login → push note → WebSocket chat → `search_notes` → `read_page` → `append_blocks` → pull the edit back. It checks tool events/results, edit records and equal Hub/device markdown. No real credentials or external service is involved. Android widget tests use the actual bridge with a loopback auth/WebSocket stub, plus phone-size light/dark golden fixtures. See [Mobile agent verification](../architecture/mobile-agent.md) for commands, results and phone steps.

**Existing limitation:** the Hub bridge currently returns an empty chat outline and revision 0; it does not expose the host's outline store. Cached chat reference cards and message-anchor navigation remain, but new chapter/section reference choices require outline metadata the Hub does not yet supply. This branch preserves the UI and does not add an outline RPC or the stage 4d desktop relay. Real Android login, deployed-Hub sync and a real provider turn still need the user's phone check.

## Integration snags

- SQLite: BubblePaw-base uses rusqlite 0.38, the vault 0.40. Both bundle SQLite, so they cannot link into one binary; BubblePaw moves to 0.40.
- BubblePaw needs tokio; the app's Rust is plain threads. The harness gets its own runtime thread.
- The `js` tool reaches other tools through `bubblepaw-core`'s `ToolDispatcher`, so vault tools only need to be registered as ordinary tools.

## Known limits

- **Store lock outlives Agent drop (BubblePaw), deferred.** Dropping an `Agent` does not always release the agent store's lock. Likely cause: the spawned `harness.drive` task (`bubblepaw-core/src/runtime.rs:269-271`) still holds a clone of the store after `Agent::shutdown` returns. BubblePaw's `Store` takes an exclusive flock on `agent.sqlite.lock` (`store.rs:123-130`) and releases it only when its last clone drops, so reopening the same data directory fails with "Database is already owned by another process". Under parallel load, `crates/agent/tests/desktop.rs` reopen tests failed this way in 7 to 17 of 80 to 96 runs. Suggested fix: `Harness::shutdown` (`runtime.rs:421-443`) joins its drive tasks; optionally `Store::open` retries the lock briefly. Test workaround: every test in `desktop.rs` takes one shared lock; remove it when the fix lands. Experiment: dropping the agent's runtime with a 5 s timeout did not fix it (15 of 80 parallel runs still failed).

## Decisions

- 2026-10-07: the agent harness is BubblePaw's Rust library, run inside the hub process next to sync.
- 2026-10-07: the code tool is BubblePaw's QuickJS `js` tool, and vault tools are exposed through it as `tools.*`.
- 2026-10-07: phones and other devices use a live agent channel on the hub connection; chats stay separate from the vault.
- 2026-10-07: hosts register with the hub over an outbound connection, so the desktop needs no open port.
- 2026-10-07: an Anthropic provider is added to BubblePaw.
- 2026-10-08: the model sees only `js`; every other tool is `tools.<name>()` inside it.
- 2026-10-09: the agent runs in Bypass only (temporary policy); permission modes stay hidden.
- 2026-10-22: PC host relay: a desktop with "Let the hub use this computer" on connects out to `/host/ws` and is the host `<device name>` on `/mcp/agent` (OAuth only, Bypass, 10-minute call timeout, no state across hub restarts).
- 2026-10-22: AI settings follow the runner: one synced "Run AI on" (Hub | This computer) and, below it, only that runner's settings; the hub's models come from the hub (`host_info.default_model` names its default); no per-device runner or model choice.
- 2026-10-20: the hub host uses BubblePaw's native tools (`execution_mode = "native"`, JS optional); the in-app agent stays in JS mode. Desktop file tools follow BubblePaw's exact-string `edit` and whole-file `write`, with no compatibility shim.
