# Architecture

Scratch is a Rust core that holds the vault, a sync layer and a hub server around it, one set of tools that the app and agents both use, and a Flutter app built as a shell, a shared kit and add-ons. This page says what each layer does and which rules hold between them. Details are in the pages each section links to.

## Layers

Each layer may depend only on the layers above it in this table.

| Layer | Where | Job | Rule |
|---|---|---|---|
| Core | `crates/core` (`vault_core`) | Pages, blocks, properties, the index, search, history, attachments, conflicts, mounts | Depends on no other crate in the repo. Knows no UI, network or agent. |
| Sync | `crates/sync` (`vault_sync`) | Moves page documents and attachments between a device and the hub | Depends on the core only. |
| Tools | `crates/tools` (`vault_tools`) | The operations agents call: create, read, edit, move, search, memory, tasks. Also holds the `notes` command-line tool, the memory rules, help topics and the wiki import. | Depends on the core, and on sync for the device-key session used by `notes setup`. |
| MCP | `crates/mcp` (`vault_mcp`) | Serves the tools to outside clients over MCP. Also holds the job, task and runner records for agent work. | Depends on the core and tools. |
| Agent | `crates/agent` (`vault_agent`) | The built-in agent, on the BubblePaw harness | Calls the same tools as outside clients. |
| Hub | `crates/hub` (`notes_hub`) | The server: sync endpoint, MCP endpoints, the built-in agent, login, the web viewer and share links | The only always-on node. |
| CLI | `crates/cli` (`scratch_cli`) | A command-line client for the agent and packages | |
| Bridge | `app/rust` and `app/lib/src/rust` | Rust-to-Dart bindings, generated by flutter_rust_bridge | The generated files are never edited by hand. CI regenerates them and fails on a difference. |
| App | `app/lib` | The Flutter app: shell, kit, add-ons | See [The app](#the-app). |

Two small crates have no dependencies inside the repo: `agent_wire` (the message types between the app and the agent) and `packages` (add-on dependencies downloaded on demand).

## Storage

- **One page is one Loro CRDT document.** The document is the truth and is what syncs.
- **A markdown file mirrors each page,** so the vault can be read without the app. Page roles and properties are in its frontmatter.
- **A SQLite index is derived from the documents.** It serves the page tree, search and live queries, and can be rebuilt from the documents at any time. Nothing lives only in the index.
- **Attachments are content-addressed files** under `.vault/blobs/`, named by their SHA-256.
- **History is per page,** from the CRDT. Old history is kept compressed on the device and is rebuilt when it is needed.

More: [data model](core/data-model.md), [core state](core/core-state.md), [sync and storage](sync/sync-and-storage.md).

## Devices and sync

- Every device holds the vault and works offline.
- Devices sync with the hub, which runs on the owner's server behind a login provider. See [the hub](sync/hub.md) and [device keys](sync/device-keys.md).
- Concurrent edits merge through the CRDT. Where a merge cannot be automatic, the conflict is recorded in the page and shown for the user to resolve. See [conflict format](core/conflict-format.md).
- The sync messages carry a version byte. There is one base message format and an envelope around it that adds purge and restore records.
- The hub renders pages for the web viewer and for share links.
- A folder on a PC can be mounted at a vault path. See [folder mounts](core/mounts.md).

## Tools and agents

- The tool list is defined in `crates/tools`. Outside assistants reach it through the hub's MCP endpoints; the built-in agent calls it directly.
- Agent memory, feedback reports and agent tasks are pages under hidden system pages.
- Help topics for agents are in [docs/notes](../docs/notes/).

More: [AI assistants](integrations/ai-assistants.md), [the agent](integrations/agent.md), [agent memory](integrations/agent-memory.md).

## The app

The app has three parts. The import rules between them are checked in CI by `scripts/check-addon-imports.dart`.

- **Kit:** shared UI (`app/lib/ui`), the registries (`app/lib/registry`) and services (`app/lib/services`). The kit imports no add-on.
- **Add-ons:** one folder each under `app/lib/addons`, compiled into the app. An add-on imports only the kit, the engine code (`app/lib/core`, `app/lib/state`, the bridge), its own folder, and the `api.dart` of add-ons it names in `dependsOn`.
- **Shell:** boots the app, holds the list of add-ons and asks the registries what to draw.

An add-on extends the app by registering, through `AddonContext`:

1. page types (the editor, card and embed for a type)
2. block kinds, with their codecs
3. view layouts
4. property kinds
5. commands and slash items
6. settings sections
7. agent tools

It can also register search sources, shell panels, navigation entries, primary actions, title chips and inline marks.

The `legacy` add-on is exempt from the import rule. It adapts older app code (`app/lib/editor`, `app/lib/blocks`, `app/lib/features`) that has not been moved into add-ons yet.

The app reaches the core through one `Vault` class (`app/lib/core/vault.dart`). It has named methods for common operations, and `run` and `raw`, which let any caller make any bridge call.

More: [add-ons](app/addons.md), [add-on reference](addons/index.md), [app state](app/app-state.md).

## Guarantees

These are the behaviours the design depends on. Each one is worth a test, and little else is.

- Rebuilding the index from the documents gives the same search results.
- A page survives the round trip through its markdown mirror.
- Two devices that edit offline converge after syncing.
- An add-on has no undeclared imports: it reaches another add-on only through the `api.dart` of a dependency it declares.
- A tool behaves the same from the MCP endpoints, the built-in agent and the app.
- A vault from the previous release opens in the next one.

## Target

The code is being brought to a smaller baseline. These changes are planned and not done:

- **Tools become a registry of operations only.** Each tool is defined once (name, input, behaviour, description). The command-line tool, the chat-outline store and the memory rules move out of `crates/tools`, and the job and task records move out of `crates/mcp`.
- **The app calls named operations.** Callers stop using `Vault.run` and `Vault.raw` directly, so the app and agents use the same operations.
- **Three concepts: page, property, type.** Every page has one type, and "Page" is the default. A type is defined vault-wide: its properties and defaults, a body template, which editor opens it, its renderings (full page, card, row or chip) and how it shows its children. A type travels with the page. No parent owns a schema; a parent may set the default type for new children. Types are built in or come from add-ons.
- **Task is a built-in type.** To-do blocks stay blocks until promoted to a Task page.
- **A view is a typed page.** Its properties are the source and the layout, and any page may open as a view of its children. Pages are the only view store.
- **A card is the card rendering of an embedded page.** Embedding is one block kind. A search card is an embedded Search page.
- **Inline views are child pages,** hidden from the page tree and from search until opened or moved. A view inside a view renders as a compact summary, one level deep.
- **An add-on ships types with their renderings,** in place of separate page types, view layouts and card renderers.
- **One-time vault conversion.** Existing `database` pages, older views and `view` blocks are converted once in the hub vault. The app ships no migration code for it.
- **Removed:** the `database` page type, the older view store, the `view` and `query` block kinds, the kanban page type, the purge envelope as a separate sync format, hidden tool aliases, the second hub binary (`vault-hub` in `crates/sync`), the `legacy` add-on, and `prototypes/`.
